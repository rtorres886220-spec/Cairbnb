# CairBnB security status

## Current deployment model

This is a static browser-only prototype. Lead records, property access instructions, crew details, messages, photos, and the local password verifier are stored in browser storage. The password screen is a UI lock only; anyone who can load the public static files can bypass it and inspect or alter browser storage. Do not use this as a secure multi-user production system or store sensitive access codes in a public deployment.

The `_headers` file applies defense-in-depth response headers on Cloudflare Pages. It does not authenticate users or protect data at rest. Its Content Security Policy allows only same-origin scripts and the known City CSV source; Google Fonts remains an external style/font dependency.

## Before using real client/crew data

1. Protect the CairBnB hostname with Cloudflare Zero Trust Access and an allow policy limited to the owner's identity (and later approved team identities). Test the hostname and the `pages.dev` preview hostname; protect or disable the preview hostname so it cannot bypass the gate.
2. Replace the local password UI with server-verified accounts, secure session cookies, role-based authorization, and MFA for owners.
3. Move records and photos to a backend with per-account authorization, server-side validation, encryption, backups, and audit logging. Keep access codes out of public/static assets.
4. Add server-side rate limiting, abuse monitoring, dependency/update management, and a tested recovery procedure.

Cloudflare Pages `_headers` are applied to static asset responses, not responses generated by Pages Functions. If Pages Functions are added, set equivalent security headers in the function responses too.
